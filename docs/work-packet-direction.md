# PR #9後の方針: 一匹に渡す仕事の粒度を測る

2026-09-11。利用者の「PRをマージし、議論を参考に方針を決める」に基づく作業上の既定値。実装と新しいモデル実走はこれからである。PR #9はPR #8のブランチへマージ済みで、mainへの取り込みは#7・#8に依存する。

## 採用する方向

Sheepを、仕事の範囲・粒度・同時実行数を選び、版と権限と全体受入を守って実行するruntimeとして育てる。N=1を正常な選択肢にする。小さい仕事をfile数だけで分割することを既定の有用性仮説に置かない。適応的な選択器はまだ実装せず、先に固定粒度の効果を測る。

優先順は、共通のpacket実行経路 → devの固定粒度比較 → 変更起点が公開された別課題でactivation比較 → 選択規則を固定して評価、とする。Manager、Cだけの増加、追加言語adapterは後へ置く。主モデルはopencode-go/deepseek-flash、thinking有効、上位0。品質と実際の受入完了までの時間を主指標とし、固定時間によるtask締切は設けない。

## 結果が支持する範囲

[PR #9の途中結果](results/synthetic-paired-dev.md)と[観測JSON](results/synthetic-paired-dev.json)を再確認した。有効39組はSingle 38/39、Sheep 37/39成功、Sheepのみ成功は0。両方成功37組中Singleが速い32組、時間比Single/Sheepの中央値0.513。同じ39組の既知token合計はSingle 495,204、Sheep 2,848,349で、比は5.75倍。target数4/8/16/32別では1.86/4.42/5.72/10.53倍。品質失敗もtoken集計へ含める。系列全体にはHTTP 500による使用量不明1callがあり、総消費は依然不明である。

independentの両方成功14組でもSingleが13勝、32targetの4組もSingleが全勝した。32targetのintervals-v09はSingleのinput 12,869tokensに対しSheep合計233,861tokens。この観測は、共通入力の反復や細かい提案の固定費が大きいという仮説と整合する。ただしcontext容量限界や遅延の原因を直接測った証明ではない。N16/C4から8waveと計算するだけでは、依存待ち・retry・実際のcall重なりを説明できない。

現行比較はSingleの全target提案と、Sheepの1target提案・全起動に加え、context、検証、retryの粒度も異なる。従って粒度だけの因果効果とは呼ばない。棄却方向に置くのは「この小さな合成repair群で現行のfile単位全起動が自然に有利」という作業仮説。一般のrepair、swarm全般、DeepSeek自体の能力限界までは結論しない。

## 次の最小実装

work packetを、許可済みtargetの集合、公開指示、配信read版、packet外依存、固定check、試行予算を持つ作業単位として表す。fileは引き続きartifactとwrite権限の単位であり、複数fileを一つの認知単位へまとめても権限を広げない。

共通executorでpacket全体の名前付き複数file提案を検査し、全件を原子的に採用または却下する。旧read版・失効権限・検査後の候補差替えを拒否し、packet内の一部だけを採用しない。packet外の変更通知と完了証拠の失効を保つ。kernelに複数writeの仕組みがあることを、repository adapterでpacket対応済みという意味にしない。

最初は決定論的な公開graphから分割する。connected component全体を常に一匹へ渡すとfanout等がallへ潰れるため、大きなcomponentは近傍で区切る。独立した小componentは同じpacketへ詰められる。循環componentや縮約後の循環を無理に切って待ち合わせ不能にせず、併合と上限超過の理由を記録する。切り方、同順位の順序、実際のpacketサイズと境界edge数はモデル実行前に固定する。意味を理解した分割器とは主張しない。

CLIは既存入口を保ち、粒度・並列上限・分割結果を指定/確認できるopt-inにする。dry-runでpacket数、target割当、read範囲、依存、上限超過理由を示す。未実装のflag名を利用可能なcommandとして案内しない。

完了条件は、packetサイズ1とall、packet内の整合変更、packet間の旧版、scope逸脱、原子的却下、循環処理、hidden非配布、usage不明時の停止を独立したfixtureと注入callerで確認すること。単体で動く全target packetも同じ経路を通す。既存Single/Sheepとの違いを疎通対照で記録し、旧結果に新方式の名前を貼らない。

## 粒度比較の設計

| 項目 | 作業上の既定値 |
| --- | --- |
| 対象 | 凍結したdev 128件。課題hash・公開仕様・oracleを保持 |
| 比較 | 共通executorのall / 最大8 / 最大4 / 最大2 / 1target packet |
| 起動 | 全target。privateの不具合位置やhidden失敗を選択に使わない |
| 並列 | 最大C4を固定。packet数、worker数、実同時call、依存待ちを別記録 |
| context | 初回は全条件で同じ公開contextを配信。read最適化は別実験 |
| 予算 | 方式間で同じ緩いcall/token枠。retryも含む。通信timeoutとtask時間を区別 |
| 順序 | 課題内の方式順を均衡化し、課題順・反復数・除外規則を実行前に固定 |
| 比較指標 | 全有効runの品質、allとの両方成功ペアの完了時間、失敗elapsed、token、call、retry、検証時間 |

allは対象target全体を指し、非公開ファイルまで渡すことを意味しない。4target課題のall/8/4など、割当が同じ条件は重複callを避けて同値条件と記録する。五方式を独立試行したかのように数えない。基準となるallを同時期に実行し、PR #9の旧Singleとの時間差を新しい粒度効果へ混ぜない。

この第一比較は認知単位と提案回数の変更を測るため、graph分割方式とread範囲は固定する。graph近傍による分割自体の有用性は、必要なら同じサイズの単純分割を追加して別に測る。時間はcall duration合計とwall timeを分け、準備・分割・全check・独立監査も記録する。

既存39組は探索に使った結果として保持する。元系列の未実行176runを最優先にはせず、停止系列を再開・上書きしない。新系列の実行manifestで対象ID、方式の同値関係、反復数、予算、runtime hashを確定するまでは新たな大量callを開始しない。

## Activationと大きな問題の評価

repair群で不具合位置が非公開なら、既知のdefectedPathsを起点へ転用しない。別にAPI/schema変更の起点が公開された課題を作り、Singleにも同じ変更要求と公開情報を与える。ここでは粒度を先に固定し、全起動/正当なimpact選択だけを変える。探索や影響判定にモデルを使えば、そのcallと時間も含める。未起動領域も全体oracleで採点する。

規模を試すときはfile数だけでなく、公開入力tokens、出力量、必要変更量、依存の幅と深さを測る。無意味なfile水増しでSingleを不利にしない。devはchain 0件・深さ1〜3であり、深い連鎖の研究には別の開発課題が必要になる。既存evaluationのchain 24件・最大31段を調整用に消費しない。

## 選択と打ち切り

devで品質を落とさず時間を短くできる粒度が見つかった領域だけを候補にする。成功の不一致は個別に保存し、小標本の同成功数を品質同等の証明にはしない。1回の最速値や課題ごとの事後最適値から適応器の成績を作らない。分割前の公開特徴だけから選ぶ単純な規則を固定し、allへ戻る選択も許す。

設定選択後にevaluationを一度の固定系列へ持ち込む。PR #8で既に観測した8件は区別して集計し、完全未見の評価とは呼ばない。family内相関と構造の分布差も明記する。どの領域でもallを上回る品質・速度が再現しなければ、その試験範囲ではallを既定とし、適応器や増員を作り込む優先度を下げる。Managerはこの判断の後に独立比較する。
