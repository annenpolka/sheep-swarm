# Luna4体の実コードpilot

実行日: 2026-09-10 JST。M2の疎通確認。個体ごとの継続記憶を追加する前のrunnerであり、人数による分業形成やM3の規模比較の証拠としては扱わない。

## 実行した作業

合成fixtureの共有APIをmilliseconds/bytesからseconds/KiBへ変更した。Lunaが4個のconsumerの単位・閾値・出力を修正し、続いて離れたconsumerを組み合わせるreportを修正した。受入は実Node子processで行い、外側の固定oracleが値、境界条件、出力キーを検査した。

下位は全呼出しでCodex CLIへ `--model gpt-5.6-luna` を指定した。上位は `gpt-6-astra` を指定。CLIはturn.completedと使用量を返したが、応答に実効モデル名は含まれていなかったため、要求モデルと独立したモデル識別の証拠は区別する。

## 必要時の介入

二つ目の実験では、consumerの出力を整数へ切り捨てる誤った共有指示を入れた。最初のLuna4呼出しは指示に従った候補を返し、受入が拒否した。上位は通常の失敗履歴を観測し、共有仕様から切り捨てを除いて小数を保持する指示へ修正した。その後、下位が通常の再試行としてconsumer4個とreport1個を修正し、全体の受入が通った。

下位から上位を呼ぶAPIや相談は使っていない。上位はworkerのコードを実装せず、仕様artifactの版付き変更として介入した。採点条件は変更していない。

## 確認できた範囲

版付き提案、局所コードの検証、確定、依存通知、最終受入までを実Lunaで接続できた。既知依存の小さなfixtureでの結果であり、未知依存の発見、一般のrepository作業、費用優位、多数個体での創発は未検証。

この段階のNは主にworker identityの数で、個体別の継続記憶はまだなかった。M3では独立したbounded memoryと過去のread近傍に基づく担当選択を追加し、Nと実行並列度Cを別に観測する。hostが実装した担当選択の効果を、自然に生じた意味的役割と混同しない。

生の呼出し結果、候補コード、kernel履歴はworktreeの `.sheep/luna-4-initial/` と `.sheep/luna-4-intervention/` に保存した。モデル出力の自己申告だけで成功とは判定せず、両runの `result.json` と `artifacts.json` に外側受入の結果と最終成果物を残している。
