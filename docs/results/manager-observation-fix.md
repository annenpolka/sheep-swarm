# Managerの観測依存を修正した追加試行

2026-09-10 JST。[集計JSON](manager-followup.json)、[全実験の使用量台帳](model-usage-ledger.json)、[実行時ソース](frozen-runtime-sources.zip)（evaluation-v4）、[元の4方式比較](comparison-findings.md)。

観測依存の不具合は解消した。修正後の通常条件は2/2成功し、誤指示条件ではstale-read拒否がゼロになった。それでも上位が丸めの誤指示を維持したまま予算へ達し、sensor2個が未完了に残った。この追加試行は、修正後に全方式を取り直した新たな本比較ではなく、Managerの不具合とモデル判断を切り分ける3runである。

## 変更と検証境界

元実装では上位が読む全sensorを仕様の継続的な依存として登録していた。仕様編集後にsensorを1個確定するだけで、他のsensor workerの前提まで失効していた。

修正版は全体計画用のsnapshotとread stampを引き続き上位へ渡し、その観測が古くなっていれば変更を拒否する。一方、仕様の継続的な依存として登録するcheckoutは仕様とsourceに限る。観測した全コード、context量、上位の使用量は記録に残し、上位の情報量を減らした比較にはしていない。

また、残予算で作業数を切り詰めた場合にもadmissionDeniedを記録する。共通oracle、promptの目的、下位Luna4体/C=4、上位Astra、500,000token上限、30,000token予約、48call、対象3試行、24round、90秒timeoutは元比較と同じ。他3方式の実行経路は変更していない。誤指示試行の失敗を受けた追加の予算拡大や救済は行わなかった。

## 誤指示試行の内訳

下位の最初の8候補は整数への丸めにより局所oracleで拒否された。その後、失敗証拠を受けた下位が6sensorと2regionを修正し、確定した。stale-read拒否、通信失敗、使用量不明は全てゼロ。拒否8候補はいずれもrejectedで、確定版を持たない。

上位の仕様編集2回は、正しい仕様への訂正2回を意味しない。最初はfloor指示を明文化し、次はregionのraw計算を追記したが、sensorのfloor指示は残した。上位の残り4callは計画3回と、空のtargetsにより拒否された計画1回だった。したがってこのrunで、上位による丸め誤指示の訂正は0回である。

最後の上位計画後には68,161tokenが残っていた。4対象のうち2呼出し分だけ予約でき、sensor4と6が確定。その後は27,872tokenとなり、次の30,000token予約を満たさず停止した。admissionDenied:trueで、総tokenの超過はなかった。sensor7と8だけがversion0、各1試行のまま残り、対象ごとの3試行上限には達していない。

固定sourceの一致と、凍結した外側oracleを用いた最終snapshotの再検査でも、未完了はsensor7と8だった。他の8成果物はversion1。reportのretries=6は同じ対象への再呼出し件数で、初回の意味的な拒否8件とは異なる集計である。

## 解釈

旧実装の過剰な失効は除去できた。残ったのは、この試行での上位の誤指示維持と、全体計画を繰り返す費用、呼出し予約の粒度による未完了である。これを中央管理一般の失敗率やSheepの普遍的な優位へ拡張しない。

必要時の介入を評価するときも、仕様編集の件数だけでは足りない。誤りが実際に訂正されたか、下位が何件やり直したか、最後の未完了を含む費用を併せて見る必要がある。
