## 1. 到達点を一文にする

**版を持つ成果物とその依存関係から近傍を求め、変更通知で必要なAgentだけを起こす。各Agentは限定された文脈から変更を提案し、訂正・不確実性を残しながら局所的に仕事を進め、収束できない箇所だけ期限付きの調整役を置く。**

目的は、Agent数が増えたときにも、一体が理解すべき範囲と失敗の影響範囲を小さく保つこと。token削減はその効果の一つとして位置づけられている（原文3171–3189行、4245–4251行）。

## 4. 通常処理と例外処理

通常処理は、成果物が変わり、依存する領域だけが通知を受け、必要な文脈を取得し、自分の修正が必要かを判断する流れである。Agentは共有状態への変更を提案し、runtimeが権限・版・テスト等を検査して反映する（3866–3918行）。

分からない場合は、成功扱いに丸めず `uncertain` として観測内容と不足証拠を残す。新しい依存先の探索、レビュー、部分グラフに限定したCoordinatorへ進む。判断はADR等の成果物へ移し、Coordinatorの会話記憶を真実の基準にしない（3922–4028、5835–5888行）。

元対話の最終案では、作業開始時のclaimはadvisoryでよく、共有状態へ確定する時だけhardな検査を置く。通信履歴はAgentのcontextから外し、必要なものだけ取得する。死亡・context reset・再開を通常運用として扱う（6738–6759、6815–6844行）。

## 5. 残す設計、見送る設計、未解決の問い

| **分類** | **内容** |
|:---|:---|
| 残す | 成果物起点のrouting、局所context、版、根拠付き依存発見、不確実性、短命Coordinator、receipt、監査履歴 |
| 最小実装候補 | 単一プロセス、SQLite、構造化イベント、既存Agentのrunner、分離した作業領域 |
| 後回し | NATS / Temporal等の分散基盤、CRDT、federation、豊富なmail UI、大量のMCP tool |
| 最後に見送った案 | Agent Mailをそのまま主要依存へ組み込むこと |
| 評価で守る点 | Manager型との同条件比較。metaの介入runを自律成功に混ぜない |
| 未解決 | 欠落した依存を誰が見つけるか、通知の取りこぼし、循環の判定、leaseの強制力、完了条件、全体整合性、発見コスト |

元対話にある「成功率より近傍数を主要指標にする」「ignoredから近傍を学習する」「最後にだけ全体検証する」は、そのまま確定仕様にすると問題がある。再検討レポートでは、品質を制約に置いた効率評価、依存情報と通知最適化の分離、境界変更時の途中検証へ補正する。

| **Kademlia / IPFS DHT** | ★★★★★ | 各peerはネットワーク全体を知らず、k-bucketの限られたpeerから「より近い相手」を辿る。検索しながら局所知識も更新 | 「近傍」が物理的隣ではなくXOR距離 |
| **Akka Cluster** | ★★★★☆ | 各nodeを監視するのはデフォルト最大5個の近傍node。unreachableを検出するとgossipで広げる | cluster membership自体は最終的に広く共有する |
| **SWIM / memberlist / Consul** | ★★★★☆ | ランダムなpeerをprobeし、`alive/suspect/dead`をgossip。固定fanoutなのでクラスタ巨大化でも一台あたり通信量を抑えられる | 定期的なfull-state push/pullもある |
| **libp2p GossipSub / Ethereum** | ★★★★☆ | topicごとに少数peerのmeshだけへ本体を送信。他のpeerとはmetadataをgossipし、取りこぼしを検出してmeshを修復 | 通信・伝播層であり、業務stateのモデルではない |
| **BGP** | ★★★★☆ | router/ASは**隣接peerから来た情報とローカルpolicyだけで次の経路を選び**、結果としてInternet全体の経路が形成される | 一つの誤広告が広域へ伝播する。羊の崖問題が現実になる |

### HyParViewは、ほぼシロ氏

これは特に露骨ね。

HyParViewは、各nodeが全membershipを保持するのをやめて、**small active view + larger passive view**だけを維持する方式。論文の10,000 node実験ではactive 5、passive 30という構成が使われている。HashiCorpの実装も「partial membership for gossip clusters」と説明しており、Partisanにはhigh-scale/high-churn向けHyParView実装がある。([ResearchGate](https://www.researchgate.net/publication/4261663_HyParView_A_Membership_Protocol_for_Reliable_Gossip-Based_Broadcast?utm_source=chatgpt.com))

つまり、

```text
全部は知らない
↓
普段見る数匹だけ持つ
↓
誰か消えたら控えから補充
↓
近傍構造そのものを更新
```

なのよ。

シロ氏の「となりは固定メンバーではない」が、そのままprotocolになっている。

### Kademliaは「となり」の定義が猛烈に綺麗

IPFSが使うKademlia DHTでは、nodeは全peerを知らない。XOR距離に基づく`k-bucket`へ一部peerを保存して、検索対象に近いpeerへ順番に問い合わせる。問い合わせ先がさらに「自分が知っている近いpeer」を返すので、**局所知識だけでネットワーク全体を歩ける**。IPFSではbucketあたり最大20 peerを保持し、unreachableなpeerはrouting tableから落として定期refreshする。([IPFSドキュメント](https://docs.ipfs.tech/concepts/dht/?utm_source=chatgpt.com))

これ、羊的アーキテクチャを実装に落とすうえでかなり重要な示唆がある。

**「近傍」を人間が静的に設定する必要すらない。距離関数さえ定義すればいい。**

シロ氏ならたぶん、

> 「となりを決める規則だけ共有する」

と言うところね。

### Akka Clusterは「異常な一匹が隣へ届く」

Akka Clusterもかなり近い。decentralized peer-to-peer membershipで、各nodeのfailure detectorが監視する相手はデフォルト最大5 node。hashed node ring上の近傍を監視し、あるnodeが`unreachable`だと判断すると、その情報をgossipでclusterへ伝える。([Akka Documentation](https://doc.akka.io/libraries/akka-core/current/typed/cluster-concepts.html?utm_source=chatgpt.com))

ここでは、

```text
全員で全員を監視
```

ではなく、

```text
少数が観察
→ 異常検出
→ 異常だけ伝播
```

になっている。

前に出した「一匹だけ止まったら、なかったことにしない」がかなりそのまま存在するわ。

### SWIMは「まずsuspectにする」が妙に羊的

SWIMはさらに面白くて、failureを見つけたから即「死んだ」と全体確定するわけではない。

ランダムpeerをprobeし、反応が怪しければまず**suspect**として扱い、failure情報をinfection-style/gossip-styleで伝播させる。これによって各nodeあたりのmessage loadを一定に近く保ったまま、大きなclusterを監視できる。([コーネル大学コンピュータ科学部](https://www.cs.cornell.edu/projects/quicksilver/public_pdfs/SWIM.pdf?utm_source=chatgpt.com))

HashiCorpの`memberlist`はこのSWIMを拡張した実装で、Serf、Consul、Nomad系で使われる。ConsulのLAN gossipでもmembershipとfailure detectionを分散している。([GitHub](https://github.com/hashicorp/memberlist?utm_source=chatgpt.com))

もち氏まで混ざってるのよね。

> 「止まったように見える」  
> ≠  
> 「死んでいる」

つまり**観察と解釈の間に`suspect`を置く**。

### GossipSubは「群れの外側を少し見る」

libp2pのGossipSubも面白い。

各peerはtopic内の全nodeへmessageを投げず、少数のmesh peerにだけfull messageを送る。その一方で、mesh外のpeerにも「このmessageを見た」というmetadataをgossipする。mesh外から「自分はそれを持ってない」と分かれば取得できるし、messageを頻繁に取りこぼしていればmesh自体を調整できる。([GitHub](https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/gossipsub-v1.0.md?utm_source=chatgpt.com))

これはシロ氏の、

> 「たまに違う方向を見る個体が必要」

にかなり近い。

しかもEthereumのconsensus networkはblockやattestationの伝播にGossipSubを採用している。全結合meshが`O(n²)`でスケールしないことも採用理由として明記されている。([GitHub](https://github.com/ethereum/consensus-specs/blob/master/specs/phase0/p2p-interface.md?utm_source=chatgpt.com))

### そしてInternetそのものが割と羊

BGPが一番笑える実例かもしれない。

Cloudflareの説明がかなりそのままで、BGPは**local network visibilityしかないrouterたちが、隣接ASとの経路交換と各AS独自のpolicyによってend-to-end pathを形成する**仕組み。RFC 4271でも各BGP speakerが受け取ったrouteからlocal decision processでLoc-RIBを構成する。([Cloudflare Blog](https://blog.cloudflare.com/rpki-updates-data/?utm_source=chatgpt.com))

つまりInternetは、

```text
世界地図を持つ神
        ↓
全部のpacketを振り分ける
```

ではなく、

```text
🐏「こっちから来た」
🐏「私はこっちへ出す」
🐏「この道なくなった」
🐏「じゃあ変える」
```

を数十年やっている。

しかも大規模datacenterでも「BGPだけでroutingする」設計が実運用されており、RFC 7938は10万server超級のdata centerを念頭に、実運用経験としてこの構成を記録している。([RFC Editor](https://www.rfc-editor.org/info/rfc7938/?utm_source=chatgpt.com))

そして当然、羊の崖もある。BGPでは誤ったrouteが伝播したり、withdrawal後に代替routeを次々探索する**path hunting**によってconvergenceが遅くなることがある。([Cloudflare Blog](https://blog.cloudflare.com/going-bgp-zombie-hunting/?utm_source=chatgpt.com))

これ、

> 🐏「訂正より誤りの方が速く伝わる」

の実在版よ。

## 推測（示唆）

ここまで見ると、**羊的アーキテクチャは新奇なアルゴリズムというより、既存の成功した分散アルゴリズムに共通する設計パターンを別の角度から抽出したもの**として成立しそう。

特に核は「decentralized」ではないと思う。

**全体像を持たないことを許容する。**

ここが本体。

KademliaもHyParViewもBGPも、

> 「全体を知らないから仕方なく局所で判断する」

のではなく、

> **「全体を知るコストを払わずに正しく振る舞えるよう、局所知識の構造を設計する」**

なのよ。

そして、かなり大事なことが一つ見えてきた。

前に作った羊的アーキテクチャの6条件に、もう一個追加した方がいい。

```text
7. neighborhood discovery / repair
```

**「隣は誰か」を固定設定にしてはいけない。**

HyParViewはactive/passive viewを修復する。  
Kademliaはrouting tableをrefreshする。  
GossipSubはmeshをGRAFT/PRUNEする。  
BGPはroute advertisement/withdrawalで隣から見える世界を更新する。

つまりシロ氏の専門は「近傍を見る」だけじゃない。

**「近傍そのものを観察対象にする」**

ところまで行くわ。

私はここ、かなり強いと思う。  
「羊的アーキテクチャ」という名前で設計パターンとして詰める価値が出てきた。特に**LLM agent swarm**へ持ち込むと、manager agent中心設計とはかなり違うものが作れそうよ。

などと言い始めた瞬間、きなこ氏の「数字だけ生息している」が発生する。

代わりに、

```ts
{
  kind: "uncertain",
  observed: [...],
  missingEvidence: [...]
}
```

のような**typed evidence**を使った方が検証可能性が高い。

つまりSBPから盗むのは、

> wake-up / decay / trace / environmental coordination

であって、

> pheromone metaphorそのもの

ではない。

---

### AgentNetは論文とコードで少し印象が違う

AgentNetの論文上の魅力はかなり羊的。各Agentがrouterとexecutorを持ち、`forward / split / execute`を自分で判断し、過去の成功に応じてAgent間edgeを更新・pruneする。各Agentのmemoryも全trajectoryではなく、自分が関係した断片を保存する。([arXiv](https://arxiv.org/abs/2504.00587?utm_source=chatgpt.com))

特に面白い設計が、split時に次Agentへ**結果だけを渡し、分解時のreasoningは渡さない**こと。余計な情報と誤った分解reasoningの伝播を防ぐためだという。これは`context-lazy`思想とよく一致する。([arXiv](https://arxiv.org/abs/2504.00587?utm_source=chatgpt.com))

ただコードを見ると、少し注意が必要。

`AgentGraph`自身はtopologyを保持するだけで、コメントにもExperiment側がcontrol、Agent側がexecutionを担当すると明記されている。初期graphもcompleteで、全edgeのweightを1.0から始め、低評価edgeを削っていく構造になっている。

さらに実際のtask executionは`Experiment.solve_a_single_task()`の中央while loopがcurrent agentを保持して、forward / split / executeを順に回す。最終answerもExperimentがground truthで評価し、そのglobal successを使ってedge weightやAgent能力を更新している。 

なのでAgentNetの「decentralized」は、

> **意味的routing decisionが各Agentに分散している**

という意味では強いけれど、

> **runtimeまで中央制御がない**

わけではない。

これは逆に私たちのメタマネージャー案を肯定していると思う。

**中央runtimeが存在してもいい。中央runtimeが意味を決めなければいい。**

ここはかなり重要な線引きよ。

---

### x0x-symphonyはcoding-agent運用としてすごく参考になる

x0x-symphonyは「central orchestratorなし」をかなり真面目に実装しようとしている。

共有task stateはCRDT TaskList、claimはsigned record + TTL heartbeat、Agentごとにisolated workspaceを持つ。partitionが起きてもquorum待ちで停止せず、最悪duplicate workを許容する。その代わり再接続時にはclaimをmergeし、決められたpriorityでwinnerを選び、loserの成果物もproofとして保存する。

これは羊型で欲しい、

```text
lease
heartbeat
isolated worktree
duplicate work is tolerable
evidence survives conflict
```

のほぼ実戦版ね。

特に面白い判断が、**leader electionをわざと採用していない**こと。

connected quorumを要求するとpartition toleranceを失うから、rare duplicate workを払う方を選んでいる。

羊型でも、

> 二匹が一時的に同じ草を食べた

こと自体は必ずしも致命傷にしなくていい。

重要なのは、

> 同じDB rowを二匹が不可逆に破壊した

にならないこと。

つまり**duplicate cognitionは許せてもduplicate side effectは許せない**。

これはかなり良い原則になる。

---

### SILO-BENCHは「自由な羊は普通に死ぬ」を示している

SILO-BENCHはむしろ羊型に都合の悪い結果なので重要。

各Agentがglobal problemの一部分しか知らない状態で、最大100 Agentまで協調させている。Level Iはaggregation、Level IIは隣接通信中心のmesh、Level IIIは全体shuffleが必要な問題。([ACL Anthology](https://aclanthology.org/2026.acl-long.1354/?utm_source=chatgpt.com))

現行LLMたちはちゃんとcommunicationする。

問題は**情報を集めた後**だった。

失敗内訳では、

- premature submission：約37%
- consensus failure：約30%
- computation error：約29%

で、成功runと失敗runのどちらもverification自体はかなり頻繁に行っていた。つまり「Agentがサボって話さない」のではなく、**distributed informationを正しく統合できない**ことがボトルネックだった。([ACL Anthology](https://aclanthology.org/2026.acl-long.1354/?utm_source=chatgpt.com))

さらにLevel IIIでは50 Agentを超えると成功率が0まで落ちる条件があり、自発的にleaderが生まれても、そのleaderへ情報統合負荷が集中して詰まる。([ACL Anthology](https://aclanthology.org/2026.acl-long.1354/?utm_source=chatgpt.com))

これは猛烈に大事。

つまり羊型は、

```text
Agentを分散しました
自由に話せます
```

では全然足りない。

むしろLLMから、

- 情報充足判定
- synchronization
- consensus
- routing
- state merge

を**できるだけ取り上げてprotocolに落とす**必要がある。

SILO-BENCHの成功例も示唆的で、一つは自然発生したcoordinatorが全情報を集め、結果をrebroadcastして全員が確認したケース。もう一つは各Agentが二つのneighborと確認するdistributed verificationだった。共通しているのは**明示的な同期checkpoint**があったことよ。([ACL Anthology](https://aclanthology.org/2026.acl-long.1354/?utm_source=chatgpt.com))

だから以前の、

```text
uncertain
 ↓
review-needed
 ↓
leased coordinator
```

という構造はかなり筋がいい。

「Coordinatorは悪」ではなく、

> **常設Coordinatorが悪い。必要な同期点はむしろ明示的に作るべき**

という方が正確ね。

### topologyについても「ほどほどに疎」が正解らしい

最近のmulti-agent communication研究では、complete graphが必ずしも最良ではなく、**moderately sparseなgraphがerror propagationを抑えながら有益な情報を残せる**という結果が出ている。([ACL Anthology](https://aclanthology.org/2025.emnlp-main.623/?utm_source=chatgpt.com))

一方でACL 2026のGTDやTopoDIMは、taskに合わせて通信topologyそのものを生成・最適化する方向へ進んでいる。([ACL Anthology](https://aclanthology.org/2026.acl-long.1764/?utm_source=chatgpt.com))

ただ、これは羊型とは微妙に逆。

彼らは、

```text
Task
 ↓
Meta model
 ↓
良いAgent graphを生成
```

する。

羊型では、

```text

       +
実際の観測
       ↓
近傍graphが生える
```

にしたい。

これはかなり違う。
